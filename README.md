## Git 형상관리 프로세스

#### main (운영 브랜치)
- 운영유지 마스터 브랜치
- 권한자에 의해서만 관리 됨.
- develop, ci-cd 브랜치만 PR을 생성할 수 있음.

#### develop
- 개발 브랜치
- main으로 부터 파생됨.
- 배포 대상인 feature 브랜치들의 merge 대상이 됨.
- PR 만 허용

#### ci-cd
- CI/CD 작업 브랜치
- main으로 부터 파생됨.
- 관리자에 의해서 관리 됨.
- 변경 사항은 `main`, `develop` 및 필요한 브랜치에 적용 됨.

#### feature
- 기능 개발 브랜치
- develop으로 부터 파생되어야 햠.
- 원격 저장소에 해당 브랜치를 `push` 해야함.
- 개발 완료 후에 develop branch에 merge 함. (브랜치는 삭제 X)
- 이름 규칙 "feature/기능 이름"

#### b-feature (1인 개발시 생략)
- 백엔드 기능 개발 브랜치
- feature으로 부터 파생되어야 함.
- 개발 완료 후에 feature 브랜치에 merge 되어야 함. (no fastforword)
- feature 브랜치에 merge 후 삭제 함.

#### f-feature (1인 개발시 생략)
- 프론트 기능 개발 브랜치
- feature으로 부터 파생되어야 함.
- 개발 완료 후에 feature 브랜치에 merge 되어야 함. (no fastforword)
- feature 브랜치에 merge 후 삭제 함.

#### docs
- 문서 작업 브랜치
- 변경 사항이 자동으로 develop 브랜치에 자동으로 merge 됨.
- `.md` 파일의 수정만 허용함.

## DB 버전 관리 규칙

### 이름 규칙
- `V{version}__{title}.sql` 형식을 사용한다.
- 버전 번호와 제목은 밑줄 두 개(`__`)로 구분한다.
- 제목은 영문 소문자와 언더스코어(`_`)를 사용한다.

### 버전 규칙
- 기본적으로 `V1`, `V2`, `V3`과 같이 정수 버전을 순차적으로 증가시킨다.
- 각 마이그레이션 파일의 버전은 고유해야 한다.
- 이미 적용된 마이그레이션 파일은 수정하지 않는다. 변경 사항이 발생하면 새로운 마이그레이션 파일을 추가한다.
- 하나의 파일은 하나의 논리적인 변경 작업을 담당하도록 작성한다. 
    - 단, 하나의 변경 작업에 여러 리소스의 변경이 필요한 경우 같은 파일에 포함할 수 있다.

### 제목 규칙
- 변경 작업의 목적과 내용을 쉽게 이해할 수 있도록 간결하게 작성한다.
    - 10단어 이하로 작성한다.
- 단일 리소스 변경은 작업 유형과 리소스명을 기준으로 작성한다.
    - 생성 : `create_{resource_name}`
    - 수정 : `modify_{resource_name}_{change_desc}`
    - 삭제 : `drop_{resource_name}`
- 여러 리소스를 함께 변경하는 경우에는 공통된 변경 목적이나 기능을 기준으로 작성한다.
    - ex) `modify_post_tag_management`, `refactor_post_history_tracking`
- 제목만으로 변경 목적으로 파악하기 어려운 경우, 파일 내부에 변경 사융와 주요 작업 내용을 주석으로 작성한다.
