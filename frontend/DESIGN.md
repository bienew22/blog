# DevLog --- Developer Blog Design System

개발자가 기술을 기록하고, 코드를 공유하며, 배운 내용을 다시 찾아보기
쉬운 개발자 블로그를 위한 디자인 가이드입니다. 글 읽기·코드 탐색·태그 기반
탐색·검색·편집 경험을 중심으로 정의합니다.

## 1. Design Overview

### 제품 목표

-   **Readable first:** 긴 기술 글도 편안하게 읽을 수 있도록 본문 폭,
    행간, 제목 계층을 명확히 합니다.
-   **Code friendly:** 코드 블록, 인라인 코드, 복사 버튼, 줄 번호를 읽기
    쉽게 표현합니다.
-   **Discoverable:** 태그, 검색, 관련 글, 이전/다음 글을 통해 콘텐츠를
    쉽게 찾도록 합니다.
-   **Quiet by design:** 장식보다 콘텐츠를 우선하며, 강조 색상은 링크와
    주요 동작에 제한적으로 사용합니다.
-   **Accessible:** 키보드 탐색, 명확한 포커스, 충분한 대비, 의미 있는
    상태 표시를 지원합니다.
-   **Theme-aware:** 라이트·다크 모드에서 색상만 바뀌며 레이아웃, 간격,
    정보 구조는 유지합니다.

### 시각적 방향

-   **Light Mode:** 밝은 중립 배경, 흰색 콘텐츠 표면, 선명한 블루 링크를
    사용합니다.
-   **Dark Mode:** 눈부심을 줄이는 짙은 차콜 배경, 한 단계 밝은 표면,
    밝은 블루 포인트를 사용합니다.
-   다크 모드는 라이트 모드를 단순 반전하지 않습니다. 각 테마의
    표면·테두리·본문 색상을 별도 토큰으로 정의합니다.
-   개발자 블로그의 신뢰감은 과도한 장식보다 일관된 타이포그래피,
    안정적인 레이아웃, 읽기 쉬운 코드에서 만듭니다.

## 2. Theme Architecture

색상을 컴포넌트에 직접 하드코딩하지 말고 의미 기반 디자인 토큰을
사용합니다.

-   모든 테마 종속 색상은 CSS 변수로 관리합니다.
-   테마 전환 시 폰트, 레이아웃, 간격, 컴포넌트 크기 및 의미 구조는
    바뀌지 않습니다.
-   링크, 선택 상태, 포커스 표시에는 테마의 강조 색상을 사용합니다.
-   성공·주의·오류 상태 색상은 주요 브랜드 색상과 구분합니다.
-   상태를 색상만으로 전달하지 말고 텍스트나 아이콘을 함께 사용합니다.

### Semantic Color Rules

-   주요 링크와 기본 액션은 테마의 `Primary`를 사용합니다.
-   오류·삭제는 빨강, 성공은 초록, 주의는 노랑 계열로 구분합니다.
-   다크 모드에서 밝은 강조 배경을 사용할 경우 텍스트 대비를 별도로
    확인합니다.
-   태그 색상만으로 태그 종류나 선택 여부를 구분하지 않습니다.
-   코드 문법 강조 색상은 본문 링크 색상과 독립적으로 관리하고, 두
    테마에서 모두 식별 가능해야 합니다.

## 4. Typography

본문의 장시간 독서를 고려해 제목과 본문을 분리하고, 코드에는 고정폭
글꼴을 사용합니다.

-   **Heading Font:** Figtree
-   **Body Font:** Pretendard 또는 `system-ui`, sans-serif
-   **Mono Font:** JetBrains Mono 또는 `ui-monospace`, monospace

  Style         Specification                      Usage
  ------------- ---------------------------------- -----------------------------
  Display       36px, bold, line-height 1.2        메인 페이지 소개 문구
  H1            32px, bold, line-height 1.3        글 제목
  H2            26px, bold, line-height 1.4        주요 본문 섹션
  H3            21px, semibold, line-height 1.45   하위 섹션
  H4            18px, semibold, line-height 1.5    세부 항목
  Body Large    18px, line-height 1.8              글 도입부 및 강조 문단
  Body          16px, line-height 1.8              기본 본문
  Body Small    14px, line-height 1.65             카드 설명, 보조 텍스트
  Caption       12px, line-height 1.5              작성일, 수정일, 조회수
  Code          14px, line-height 1.7              코드 블록
  Inline Code   0.9em, monospace                   본문 내 식별자 및 짧은 코드

### Reading Rules

-   본문 콘텐츠 폭은 일반적으로 `680–760px`를 기준으로 합니다.
-   긴 문단은 적절히 나누고 문단 사이에 충분한 간격을 둡니다.
-   한 페이지에서 제목 단계는 순서대로 사용하고, 시각적 크기만을 위해
    제목 레벨을 건너뛰지 않습니다.
-   URL, 클래스명, 메서드명처럼 긴 문자열은 레이아웃을 깨뜨리지 않도록
    줄바꿈 규칙을 적용합니다.
-   코드와 본문을 같은 글꼴로 표현하지 않습니다.

## 5. Layout and Spacing

-   **Base unit:** 8px
-   **Spacing scale:** 4, 8, 12, 16, 24, 32, 48, 64, 80px
-   **Article width:** 720px 권장, 최대 760px
-   **Main container:** 넓은 화면에서 최대 1200px
-   **Header height:** 약 64px
-   **Card padding:** 20--24px
-   **Article section spacing:** 32--48px
-   **Mobile page gutter:** 16px
-   **Desktop page gutter:** 24--32px

레이아웃은 반응형으로 구성합니다. 데스크톱에서는 본문 옆에 목차나
사이드바를 둘 수 있지만, 좁은 화면에서는 본문을 우선하고 보조 영역은
접거나 아래로 이동합니다.

## 6. Border Radius and Elevation

  Token      Radius Usage
  -------- -------- -----------------------------
  None          0px 구분선, 표 내부
  Small         4px 인라인 배지, 작은 상태 표시
  Medium        8px 버튼, 입력창, 카드
  Large        12px 모달, 드롭다운
  XL           16px 소개 영역, 주요 랜딩 카드
  Full       9999px 아바타, 태그 칩

기본 radius는 8px입니다. 카드와 패널을 모두 강한 그림자로 표현하지 말고
테두리와 배경 차이로 계층을 만듭니다.

-   Subtle: `0 1px 2px rgba(15, 23, 42, 0.05)`
-   Medium: `0 4px 12px rgba(15, 23, 42, 0.08)`
-   Dark Mode에서는 그림자만으로 영역을 구분하지 말고 표면색과 테두리를
    함께 사용합니다.

## 7. Core Blog Components

### Header and Navigation

-   좌측에는 블로그 로고 또는 사이트명을 둡니다.
-   주요 메뉴는 글 목록, 태그, 소개 등 핵심 목적에 한정합니다.
-   우측에는 검색과 테마 전환을 배치합니다.
-   모바일에서는 메뉴를 축약하되 검색과 테마 전환을 쉽게 찾을 수 있게
    합니다.
-   현재 메뉴는 색상뿐 아니라 밑줄, 배경 또는 `aria-current` 등으로도
    표시합니다.

### Post List Card

글 목록 카드에는 다음 정보를 일관된 순서로 표시합니다.

1.  제목
2.  한두 문장의 요약
3.  태그
4.  작성일 또는 수정일
5.  읽는 시간이나 조회수(서비스에서 실제 제공하는 경우)

카드 전체를 클릭 가능하게 만들 경우 내부 링크와 버튼의 중첩을 피합니다.
hover 효과는 콘텐츠 탐색을 돕는 정도로 제한합니다.

### Article Page

-   글 제목, 요약, 작성일, 수정일, 태그를 본문보다 먼저 보여줍니다.
-   본문은 읽기 폭을 제한하고 제목·문단·목록·인용·표·이미지·코드 블록
    사이에 명확한 간격을 둡니다.
-   목차는 H2/H3를 기준으로 생성하고 해당 제목으로 이동할 수 있어야
    합니다.
-   이전 글, 다음 글, 관련 글은 본문을 다 읽은 뒤 자연스럽게 발견할 수
    있는 위치에 둡니다.
-   게시글이 없거나 삭제된 경우 빈 화면 대신 원인과 다음 행동을
    안내합니다.

### Tags

-   태그는 둥근 칩 형태로 표시하고, 클릭하면 해당 태그의 글 목록으로
    이동합니다.
-   선택된 태그는 배경·테두리·텍스트 대비를 함께 변경합니다.
-   태그별 글 수는 실제 데이터가 제공될 때만 표시합니다.
-   태그가 없는 글과 검색 결과가 없는 상태를 서로 다른 안내 문구로
    구분합니다.
-   긴 태그명은 레이아웃을 밀어내지 않도록 줄바꿈하거나 적절히
    제한합니다.

### Search

-   입력창에는 항상 명확한 라벨 또는 접근 가능한 이름을 제공합니다.
-   검색어가 없을 때, 결과가 있을 때, 결과가 없을 때, 검색 중일 때의
    상태를 구분합니다.
-   결과 제목과 함께 일치한 요약이나 태그를 제공할 수 있습니다.
-   검색 실패 시 사용자가 검색어를 수정하거나 전체 글 목록으로 돌아갈 수
    있게 합니다.

### Code Blocks

-   코드 블록은 본문과 구분되는 표면색, 테두리 또는 여백으로 표현합니다.
-   긴 코드는 가로 스크롤을 허용하고 페이지 전체 너비가 넘치지 않도록
    합니다.
-   복사 버튼은 키보드와 스크린 리더에서도 사용할 수 있어야 하며, 복사
    성공 여부를 텍스트로 알립니다.
-   줄 번호는 코드 탐색에 도움이 될 때만 표시합니다.
-   코드 블록의 언어를 알고 있다면 표시하되, 언어 라벨이 코드 내용을
    가리지 않게 합니다.
-   인라인 코드는 짧은 식별자나 명령에 사용하고 여러 줄 코드에는
    사용하지 않습니다.
-   문법 강조는 색상 대비를 확보하고 색상만으로 토큰 종류를 전달하지
    않도록 합니다.

### Markdown Content

-   `blockquote`는 인용임을 시각적으로 분명히 하되 본문과 지나치게 다른
    색을 사용하지 않습니다.
-   표는 작은 화면에서 가로 스크롤 또는 적절한 대체 레이아웃을
    제공합니다.
-   이미지에는 의미 있는 대체 텍스트를 작성하고 장식용 이미지는 빈 대체
    텍스트를 사용합니다.
-   외부 링크는 링크 목적이 문맥에서 분명해야 합니다.
-   경고·정보·성공 안내 블록은 아이콘과 텍스트를 함께 사용합니다.

### Forms and Editor

글 작성·수정 기능이 있다면 다음을 지킵니다.

-   제목, 본문, 태그 등 각 입력 필드에 지속적으로 표시되는 라벨을
    제공합니다.
-   필수 항목은 텍스트나 기호로 분명히 표시하고, 제출 오류는 해당 필드
    근처에 설명합니다.
-   저장, 게시, 임시 저장, 취소 동작을 시각적으로 구분합니다.
-   삭제나 되돌리기 어려운 동작은 확인 단계를 제공하고 동작의 결과를
    명확히 알립니다.
-   저장 중에는 중복 제출을 방지하고 성공·실패 상태를 알립니다.

### Empty and Error States

-   글이 없는 상태, 태그 글이 없는 상태, 검색 결과 없음, 로딩 실패를
    각각 구분합니다.
-   빈 상태에는 간결한 설명과 다음 행동(글 목록으로 이동, 검색어 변경
    등)을 제공합니다.
-   오류 메시지는 원인과 사용자가 할 수 있는 조치를 가능한 한 함께
    안내합니다.
-   장식용 일러스트는 메시지보다 시선을 끌지 않도록 하고 라이트·다크
    테마 모두에서 자연스럽게 보여야 합니다.

## 8. Interactive States

모든 인터랙티브 요소는 기본·hover·active·focus·disabled 상태를
정의합니다.

### Buttons

-   Primary: 글 작성, 저장, 게시 등 가장 중요한 동작에 사용합니다.
-   Secondary: 취소, 보조 작업에 사용합니다.
-   Ghost: 툴바, 아이콘 액션 등 시각적 무게가 낮은 동작에 사용합니다.
-   Destructive: 삭제 등 되돌리기 어려운 동작에 사용하며 빨강 계열을
    유지합니다.
-   일반 버튼 높이는 40--44px 이상을 권장하고, 작은 화면에서도 충분한
    터치 영역을 확보합니다.
-   비활성 버튼은 불투명도만 낮추지 말고 배경·텍스트·테두리 차이로
    구분합니다.

### Inputs

-   기본 높이는 44px를 권장합니다.
-   placeholder를 라벨 대신 사용하지 않습니다.
-   focus 상태는 테마의 강조 색상으로 명확하게 표시합니다.
-   오류 상태는 오류 테두리와 설명 문구를 함께 제공합니다.
-   비활성 입력은 읽기 전용 입력과 시각적으로 구분합니다.

### Links

-   본문 링크는 주변 텍스트와 구분될 수 있어야 합니다.
-   hover뿐 아니라 키보드 focus에서도 링크 위치를 알아볼 수 있어야
    합니다.
-   새 탭으로 열리는 링크는 필요한 경우 사용자에게 그 동작을 알려줍니다.

## 9. Accessibility

1.  일반 텍스트는 WCAG AA 기준 대비율 4.5:1 이상, 큰 텍스트는 3:1 이상을
    목표로 합니다.
2.  실제 사용되는 모든 전경·배경 조합을 라이트와 다크 모드 각각에서
    검증합니다.
3.  키보드만으로 내비게이션, 검색, 글 읽기, 편집 기능을 사용할 수 있어야
    합니다.
4.  모든 인터랙티브 요소에 눈에 띄는 포커스 표시를 제공합니다.
5.  의미 있는 이미지에는 대체 텍스트를 제공합니다.
6.  제목 구조와 랜드마크를 의미에 맞게 사용합니다.
7.  상태나 오류를 색상만으로 표현하지 않습니다.
8.  코드 블록, 표, 모달, 드롭다운은 키보드 및 보조 기술로 사용할 수
    있어야 합니다.
9.  애니메이션을 줄이도록 설정한 사용자를 위해
    `prefers-reduced-motion`을 고려합니다.
10. 터치 대상은 가능한 한 44×44px 이상으로 확보합니다.

## 10. Responsive Behavior

-   **Mobile:** 한 열 레이아웃, 본문 전체 폭 사용, 좌우 16px 여백,
    코드와 표는 내부 스크롤을 허용합니다.
-   **Tablet:** 본문 폭을 적절히 제한하고 보조 메뉴를 필요에 따라
    노출합니다.
-   **Desktop:** 중앙 정렬 본문과 선택적 목차·사이드바를 사용합니다.
-   화면이 좁아져도 본문 글자 크기를 과도하게 줄이지 않습니다.
-   긴 제목, 긴 URL, 긴 코드 줄, 태그가 레이아웃을 깨뜨리지 않는지
    확인합니다.

## 12. Do's and Don'ts

### Do

-   글 읽기와 코드 가독성을 가장 중요한 기준으로 둡니다.
-   태그, 검색, 목차를 통해 콘텐츠를 쉽게 탐색하도록 합니다.
-   라이트·다크 모드에서 같은 정보 구조와 간격을 유지합니다.
-   모든 색상과 인터랙션 상태를 의미 기반 토큰으로 관리합니다.
-   실제 콘텐츠 길이와 모바일 화면을 기준으로 레이아웃을 검증합니다.
-   빈 상태와 오류 상태에 다음 행동을 안내합니다.

### Don't

-   의료 서비스 전용 시각 언어와 환자 관리 UI를 개발자 블로그에 그대로
    사용하지 않습니다.
-   모든 카드에 강한 그림자나 장식을 적용하지 않습니다.
-   본문 폭을 지나치게 넓혀 한 줄이 너무 길어지게 하지 않습니다.
-   코드 블록을 본문과 같은 배경·글꼴로 표현하지 않습니다.
-   링크와 선택 상태를 색상만으로 구분하지 않습니다.
-   placeholder를 라벨로 대체하거나 오류 메시지를 숨기지 않습니다.
-   다크 모드에서 배경을 단순히 검정색으로 바꾸는 것으로 끝내지
    않습니다.

## 13. Final Design Principle

DevLog는 개발자가 작성한 콘텐츠가 중심이 되는 블로그입니다. UI는 기술
내용을 돋보이게 하되 경쟁하지 않아야 합니다. 일관된 타이포그래피, 절제된
블루 포인트, 편안한 본문 폭, 명확한 코드 블록, 안정적인 라이트·다크
테마를 통해 글을 쓰고 읽고 다시 찾는 경험을 지원합니다.
